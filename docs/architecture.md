# Устройство приложения

## Границы

- `core/` — цены, расчёт стоимости, бюджет, пороги, хранение и уведомления.
- `adapters/opencode/` — события OpenCode V2, HTTP-заголовки и подстановка цен.
- `adapters/telegram/` — локальный long polling, авторизация владельца и отчёты.
- `desktop/Sources/` — нативная SwiftUI/AppKit-панель. Она читает локальные записи,
  не опрашивает модели и не держит Telegram-процесс.
- `bin/desktop-cli.ts` — точка входа упакованного CLI; `desktop/launcher.swift`
  запускает его через Bun внутри приложения.
- `desktop/build.sh` — сборка `.app` из allowlist исходников, без личного конфига,
  ключей и данных. Готовые приложения не перезаписываются.

Исходники извлечены из локального `litellm-spend` 1.2.0 и прежней панели
OpenCode Spend. Бюджет, график, сессии и алерты сохранены. Все настройки находятся
в нижней карточке панели; маленькое меню оставлено для навигации и выхода.
Из `gold_ops` и личной адаптации
`git-graph-desktop` взят подход к изоляции GitHub; код графа и Electron не используются.

## Данные и процессы

Путь конфига по умолчанию сохранён для совместимости:
`~/.config/opencode/plugins/litellm-spend/config.json`. Нативная панель и CLI
также принимают `LITELLM_SPEND_CONFIG`; хранилище задаётся через `storage.dir`
или `LITELLM_SPEND_DIR`. Адаптер читает `config.json` рядом со своим пакетом.

Новый ключ из окна подключения сохраняется в `~/.config/litellm-spend/key`
с правами `600`, не в JSON. Поле ключа не заполняется текущим секретом.
Пороги и UTC-час сброса редактируются прежним окном настроек.

Адаптер работает внутри OpenCode, панель — отдельно, Telegram — отдельным
LaunchAgent. Запуск панели не перезапускает службы и не включает рассылку.
При ручной переустановке Telegram-службы из CLI её plist ссылается на runtime
и JS внутри `.app`: сначала поместите приложение в постоянную папку.
Не перемещайте его после такой установки без переустановки службы.

Сессии учитывают только наблюдённые шаги LiteLLM с `accountingVersion: 2`.
Общий бюджет ключа может включать расходы других клиентов. Формула кеша:
`read / (input + read + write)`; это доля токенов, а не скидка.

Дневной лимит ключа берётся из заголовка LiteLLM `x-litellm-key-max-budget`.
Параллельные ответы приходят не по порядку, поэтому график и темп строятся
по накопленному максимуму показаний; показание ≤ 0 начинает его заново.
Темп — прирост за последние `forecast.windowMinutes` по часам, окно начинается
не раньше начала периода и не короче `forecast.minSpanMinutes`. Пауза снижает
темп до нуля вместо сообщения о нехватке данных. Прогноз к сбросу — текущий
расход плюс этот темп. Один расчёт реализован дважды: `forecastKey` в
`core/rules.ts` для CLI, Telegram и алертов и `DailyPace` в панели, которая
пересчитывает его каждые 5 секунд. Плагин передаёт окно в `status.json`
(`paceWindowMinutes`, `paceMinWindowMinutes`); без этих полей от старого
плагина панель берёт значения `config.defaults.json`. Поле `forecast.minWindowSpendUsd`
устарело и игнорируется. На графике прогноз — одна пунктирная линия с подписью
итога в конце, легенда рисует образцы реальных линий. Предел — остаток,
делённый на время до сброса, выводится только текстом.
CLI и Telegram считают месячную норму «Можно в день» по той же формуле, что панель.
Личный месячный бюджет `planningBudget.monthlyUsd` не меняет серверный лимит ключа.
Он относится к календарному месяцу с первого по последнее число, UTC, независимо
от даты начала сбора истории. Карточка явно показывает границы месяца; при смене
месяца не подставляет старую оценку вместо отсутствующих новых данных.
Расход по дням неравномерный, поэтому норма «Можно в день» не равна бюджету,
делённому на число дней. Её считают как остаток на начало текущего UTC-дня,
делённый на число дней до конца месяца, включая сегодня, но не выше лимита ключа.
Пунктир на графике идёт только по оставшимся дням. Сегодняшний столбец
становится оранжевым, если расход превысил норму. «Дни по лимиту» показывают,
на сколько дней с полным лимитом ключа хватит остатка.
Устаревшее поле `planningBudget.dailyUsd` игнорируется и удаляется при сохранении
настройки в панели. Месячный итог —
локальная оценка по максимуму показаний ключа за каждый UTC-период; отсутствующие
дни, другие ключи и расход после последнего ответа неизвестны. Сырые показания
сохраняются без срока удаления и увеличивают объём хранилища. Источник актуального
фактического расхода — LiteLLM, а не эта оценка. Внутридневное падение счётчика
само по себе не доказывает сброс.
Месячная карточка показывает дневные максимумы столбиками, месячный ориентир —
пунктиром. Дни без наблюдений отмечены отдельно, не заполнены нулями; будущие дни
остаются пустыми. `monthlyEstimate.days` передаёт ту же разбивку, из которой
получена сумма. Старый статус без разбивки читается без выдуманного графика.

Собственные шаги каждой сессии хранятся отдельно. Для известных предков OpenCode
сумма с сабагентами вычисляется при чтении, без повторной записи их стоимости.
Крупная сумма в строке сессии включает её собственные расходы и всех известных
потомков. Нижняя подпись разделяет расходы основной сессии и сабагентов.
Исторические записи без связи и ненаблюдённые шаги не восстанавливаются; суммы
сессий — оценки. Записи сессий также сохраняются без автоматического удаления.

## Резервный дневной бюджет

Отрицательный расход LiteLLM включает локальный режим до 00:00 UTC. Положительные
показания в тот же день его не выключают. На следующий UTC-день снова используется
серверный счётчик; новое отрицательное показание снова включает резерв. Машинный
отрицательный хвост около нуля нормализуется прежним парсером заголовков.

Резерв суммирует собственные наблюдённые шаги LiteLLM за весь UTC-день, без итогов
предков и без добавления серверного счётчика. Цена берётся из каталога LiteLLM,
при её отсутствии — из стоимости шага агента. Шаг без обеих цен отмечается как
неоценённый, а не как бесплатный. Другие клиенты и пропущенные события неизвестны.
Без шагов с известной ценой и без поправки прогноз недоступен, а день не считается
нулевым расходом в месячной истории.
Старые суммы сессий нельзя разложить по дням: резервная история начинается после
обновления адаптера, более ранний расход нужно внести ручной поправкой.

`SessionRecord.budgetSteps` содержит ID, время выполнения, время получения и цену
каждого шага. Массив сохраняется атомарно вместе с собственной стоимостью сессии
и `appliedStepIds`; отдельной записи денежной операции нет. Параллельные шаги,
сабагенты и повторы событий не добавляют одну стоимость дважды.

Поправка задаёт итог выбранного UTC-дня на момент сохранения, а не дельту. В файле
`budget-corrections/<начало-UTC-дня>.json` хранятся сумма, время и ID уже учтённых
шагов. Итог равен поправке плюс стоимость шагов, которых нет в этом снимке.
Повторная поправка заменяет предыдущую; допустимы снижение и ноль. Запоздавшие
события относятся к дню выполнения шага, даже если получены после полуночи.
Поправка не меняет стоимость сессий и не отправляет уведомления при сохранении.

Шаги, поправки и публикация статуса сериализуются общим `budget.lock`, затем при
записи сессии берётся её собственный замок. Сеть выполняется только после выхода
из замков. При аварии после записи сессии бюджет восстанавливается из её шагов;
`status.json` — только обновляемое представление, не отдельный денежный счётчик.
Перед ручным удалением замка проверьте PID владельца, как для замков сессий.

Исходные заголовки остаются в `samples/` без изменений. В локальном режиме статус
передаёт `budget` с источником `local` или `manual`, исходным расходом LiteLLM,
числом шагов и неоценённых шагов, а также `budgetSamples` для графика и темпа.
После поправки график начинается с исправленной суммы: её изменение не считается
темпом расхода. Панель, CLI, Telegram и бюджетные алерты используют один итог;
строка OpenCode помечает его знаком `≈`. Месячная оценка для такого дня берёт
локальный итог вместо серверного максимума, даже если поправка его уменьшает.

В панели действие «Исправить расход…» открывает выбор дня и ввод суммы в USD.
Форма вызывает упакованный CLI `correct-day YYYY-MM-DD USD` без сети, через общее
ядро и замок. Дни в будущем и некорректные суммы отклоняются. Рабочие конфигурация,
службы и состояние Telegram при этом не изменяются.

Новые писатели сериализуют чтение, расчёт и запись одной сессии через файл
`sessions/<id>.json.lock`. ID применённых шагов сохраняются вместе с суммой
атомарным rename; временные отметки `steps/` остаются для совместимости.
Сетевые уведомления выполняются после освобождения замка. Ожидание замка —
до пяти секунд; замок не отбирается по возрасту. После аварии владельца проверьте
его PID в файле и завершение процесса перед ручным удалением конкретного замка.
Старые писатели этот протокол не поддерживают: после установки нужна штатная
перезагрузка всех location OpenCode, без перезапуска службы. Перезагрузка отменяет
ожидающие разрешения и формы; работающие сессии продолжаются на границе шага.

## Проверки

`bun run check` проверяет типы ядра, Telegram и CLI, тесты поведения и GitHub-изоляцию.
Типы SDK OpenCode и TUI в этот TypeScript-набор не входят: их SDK поставляет host.
`bun run build` компилирует Swift и проверяет подписи готового bundle.
`bun run smoke` запускает нативный self-test и CLI из `.app`, принимает тестовый
расход, проверяет выключенную доставку Telegram и рендерит светлую и тёмную панели.
Все записи smoke находятся во временном каталоге; ключи и сеть не используются.

Интерактивные привязка Telegram, регистрация автозапуска, установка адаптера
в рабочий OpenCode и проверка на Intel не входят в smoke.
